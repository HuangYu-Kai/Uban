# ⏱️ Ollama 地端對話服務延遲與效能實測報告

本報告詳細記錄了針對 Uban 系統的地端 AI 對話服務 (Ollama) 進行優化後的延遲表現與實測數據。測試基於地端執行之 `gemma4:e4b-it-q4_K_M` (8B) 模型，透過 Tailscale 網路連線進行。

---

## 1. 核心優化項目說明

為了解決原先 AI 對話等待時間過長的問題，我們實施了以下兩項核心優化策略：

1. **地端雙階段串流 (Two-Stage Streaming)**：
   * **優化前**：第一階段為了檢測工具呼叫 (Tool Calling)，採用同步阻塞（Non-streaming）方式，導致一般閒聊（無需工具）也必須等待模型完整生成後才一次性輸出，首字回應時間 (TTFT) 長達數秒。
   * **優化後**：第一階段改用 `stream=True`。在串流迭代中即時輸出普通對話文字；一旦檢測到 `tool_calls`，則中斷並攔截串流、執行對應工具後，將結果塞回 Context 發起第二階段串流，兼顧「閒聊極速響應」與「工具功能完整性」。
2. **工具 Schema 精簡**：
   * **優化前**：工具清單中包含 `get_elder_context`。然而長輩背景早已在 System Prompt 中載入，這導致模型在做決策時產生不必要的推理負擔。
   * **優化後**：在 `_generate_tool_schemas` 中過濾並排除此工具註冊，大幅減輕 Ollama 在決策工具調用時的推理與匹配時間。

---

## 2. 實測回應時間數據 (Latency Metrics)

我們使用實測腳本 `tests/test_latency.py` 進行了實際連線效能測試，在模型載入後的熱啟動 (Warm-start) 狀態下，測得的具體數據如下：

## 3. 結論與後續建議

* **快取生效後反應極佳**：在 Prompt Cache 作用下，複雜的工具呼叫僅需 **3.7 秒** 就能做出決策，整個工具閉環在 **5.6 秒** 內完成，極大提升了日常互動的流暢感。
* **首發延遲主要來自 System Prompt 評估**：由於 `SOUL.md` 與長輩背景資料較長，Ollama 在無快取的情況下評估 Prompt 需約 10 秒。
* **後續建議**：
  * 保持 Ollama 服務的 `keep_alive` 時間設長一些（例如 30m 或 1h），以確保模型不會因為長時間無人使用而被移出顯存。
  * 可以在長輩登入或打開 App 時，由前端或後端在背景發送一個簡短的「預熱（Warm-up）」請求，藉此提前在背景建置數據庫連接池與加載 Prompt 快取，徹底消除長輩第一句話的等待感。
